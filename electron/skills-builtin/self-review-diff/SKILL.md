# 提交前自审 diff

写代码时你在想"怎么让它工作",审查时要换成"这里会怎么坏"。**必须真的看一遍 diff**,凭记忆回想改了什么是不够的。

## 先看全貌

```bash
git status --short
git diff --stat
git diff            # 逐行看,不要跳过
git diff --cached   # 已暂存的也要看
```

改动文件数超出预期,通常意味着手滑改了不该改的。

## 逐项检查

### 调试残留

```bash
git diff | grep -nE '^\+.*(console\.log|print\(|debugger|TODO|FIXME|XXX|注释掉|临时)'
```

### 密钥泄漏(最高优先级)

```bash
git diff | grep -nEi '^\+.*(api[_-]?key|secret|token|password|sk-[A-Za-z0-9]{20,})\s*[=:]'
```

**任何真实密钥都不能进代码、配置或文档**,即使是测试用的。密钥应该走环境变量或系统钥匙串。如果发现已经提交过,除了删除还要**提醒用户去吊销重发** —— 提交历史里的密钥等于已泄漏。

### 被误删的东西

`git diff` 里的 `-` 行同样重要。逐行确认:每一处删除都是有意的吗?尤其注意大段替换时顺手删掉的边界处理、错误分支、注释。

### 范围蔓延

对每个改动问一句:**这是这次任务要求的吗?**

顺手改的格式化、重命名、"优化"会让 diff 变大、审查变难、回滚变危险。想改就单独提一次。

### 错误处理

- 新增的异步调用有没有失败分支?
- 新增的 `catch` 是不是把错误吞了?(至少要记日志)
- Node 里新增的 `spawn`/EventEmitter 有没有挂 `'error'` 监听?**没挂会直接把进程干掉。**

### 一致性

新代码和周围代码的风格一致吗?命名、错误消息语言、日志格式、注释语言 —— 不一致的地方后面每个人都要多花时间。

## 提交信息

说清**为什么**,不是**改了什么**(改了什么 diff 里有):

```
修复长任务因代理 CONNECT 503 中断后不自动续跑

代理节点不稳定时会间歇性返回 503,原先归类为不可重试,
导致长任务直接失败。现纳入瞬时错误并加真实报错回归用例。
```

## 最后

自审发现的问题,**改完要重新跑验证**。审查本身也可能引入新问题。
