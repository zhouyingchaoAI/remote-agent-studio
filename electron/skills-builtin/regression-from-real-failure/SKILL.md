# 用真实故障写回归测试

**规则:每个修好的 bug,都要留下一条能在它复发时立刻报警的测试。**

编造的测试样本会漏掉真实数据里的怪异之处 —— 多余空格、混合编码、意外的换行、超长字段。真实故障数据是最好的测试输入,而且是免费的。

## 步骤

### 1. 抓原始数据

修 bug 时你手上一定有:报错原文、日志片段、用户截图里的文字、失败的请求体。**原样保留**,不要"清理"它。

### 2. 写成测试,注释写清出处

```js
test('识别代理侧故障(截图里的真实报错)', () => {
  // 出处:用户 2026-08-11 反馈,长任务中断
  const real = 'stream disconnected before completion: URL error: '
    + 'Proxy connection failed: HTTP CONNECT failed with status 503';
  assert.ok(isTransientAgentError(real));
});
```

注释里写**什么时候、什么场景**遇到的。半年后有人想删这条测试时,这行注释就是它存在的理由。

### 3. 先看它失败

把修复回退掉(或先写测试再修),确认测试**真的会红**。一条永远绿的测试等于没有。

```bash
git stash && npm test   # 应该失败
git stash pop && npm test  # 应该通过
```

## 测试失败时:先判断谁错了

测试红了有两种可能,**必须先判断是哪一种**,判断依据要写出来:

| 情况 | 处理 |
|---|---|
| 代码错了 | 改代码。这是常态 |
| 测试写错了(断言与真实需求不符) | 改测试,**并说明为什么原来的断言是错的** |

绝不能因为"改测试比较快"就改测试。也不能因为"测试是我写的所以肯定对"就硬改代码 —— 两个方向的教条都会出错。

## 边界值也要来自现实

不要只测 happy path。真实故障往往在边界:

- 空值、空字符串、只有空白字符
- 超长输入(用户真的会粘贴 10MB 的日志)
- 非 ASCII:中文、emoji、全角标点
- 同时命中多条规则时的优先级

## 反例

```js
// ❌ 编造的样本:太干净,测不出真实问题
assert.ok(isError('error'));

// ✅ 真实样本:带完整前后文和噪音
assert.ok(isError('{"type":"result","is_error":true,"result":"API Error: Connection closed mid-response."}'));
```
