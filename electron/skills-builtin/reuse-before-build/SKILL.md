# 先找现成的,再自己写

**自己写是最后选项,不是第一选项。** 重复造轮子的代价不只是当下多花时间,而是永久多一份要维护、要测试、会有 bug 的代码。

## 三层查找,按顺序来

### 第一层:这个代码库里已经有了吗

最常见的浪费是**在同一个项目里写第二遍**。

```bash
# 按功能关键词找
grep -rniE "重试|retry|backoff" --include='*.js' -l . | grep -v node_modules
# 按函数名找
grep -rn "function.*[Pp]arse" src/ electron/ | head -20
# 看看有哪些工具模块
ls src/utils src/lib electron/*.js 2>/dev/null
```

同时看清项目**已有的约定**:错误怎么抛、配置怎么读、日志怎么打、测试怎么写。新代码要跟着走,不要另起一套。

### 第二层:依赖里已经装了吗

```bash
cat package.json | grep -A30 '"dependencies"'
```

项目里已有的库,用它比新增一个依赖好得多 —— 不增加体积、不增加供应链风险、团队已经会用。

### 第三层:有成熟开源方案吗

需要新能力时,先搜再写。判断能不能用,看四点:

1. **许可证** —— GPL 会传染到你的项目,MIT/Apache-2.0 安全。不确定就先看 LICENSE 文件
2. **维护状态** —— 最近一次提交、issue 响应速度
3. **体积与依赖** —— 为一个小函数引入 50 个传递依赖不划算
4. **契合度** —— 需要大量适配的"现成方案"往往比自己写还贵

> 许可证冲突时的折中:通过**进程隔离**(HTTP 调用、CLI 调用)使用 GPL 软件,通常不构成衍生作品。但涉及商业发布时应当确认。

## 什么时候该自己写

- 需求很小(十几行),引入依赖不划算
- 现成方案的抽象跟你的场景不匹配,适配成本高于重写
- 这是项目的核心差异化能力 —— 核心竞争力不外包

## 动手前先说清楚

在写第一行代码前,用一段话说明:

> 找过了:项目里的 X 做了类似的事但只覆盖 A 场景;依赖里的 Y 不支持 B;
> 开源的 Z 是 GPL 不能用。所以决定自己写,放在 <文件>,复用现有的 <约定>。

这段话如果写不出来,说明还没找够。

## 反模式

- 不看现有代码直接新建文件,结果和已有实现并存、行为还不一致
- 为了"更干净"重写已经能跑的模块 —— 除非有明确收益,否则这是在制造回归风险
- 复制粘贴现有函数改两行,而不是把它参数化后共用
