# 根因优先

**规则:在能用一句话说清"为什么会这样"之前,不要改代码。**

猜测式修改的代价不是浪费一次尝试,而是引入你不理解的新状态,让下一次定位更难。

## 定位流程

### 1. 拿到完整证据

不要只看最后一行报错。

```bash
<复现命令> 2>&1 | tail -50    # 完整堆栈,不是摘要
```

关键信息:哪个文件哪一行、什么类型的错、**第一次**出现在哪里(不是最后一次)。

### 2. 稳定复现

能稳定复现之前,任何"修好了"都是错觉。

- 复现不了 → 先解决复现问题:加日志、放宽条件、找出触发时机
- 间歇性故障 → **重复采样**,单次成功不能证明修好了

```bash
for i in $(seq 1 10); do <命令> >/dev/null 2>&1 && echo ok || echo FAIL; done
```

### 3. 缩小范围

二分法比通读代码快得多:

- 什么时候是好的?`git log`、`git bisect`
- 换个输入还错吗?换个环境还错吗?
- 把可疑部分单独拎出来跑最小复现

### 4. 说出机制

动手前先写清楚这句话:

> 因为 **A**,导致 **B**,所以出现 **C**。

写不出来就是还没定位到。这时候继续查,不要开始改。

## 禁止的"修复"

| 反模式 | 为什么是错的 |
|---|---|
| `try { ... } catch {}` | 错误还在,只是看不见了,后面会以更难查的形式爆发 |
| 加 sleep / 重试 绕过时序问题 | 掩盖了竞态,负载一高就复发 |
| 改测试断言去迁就代码 | 除非你能论证测试本身写错了,否则这是在删证据 |
| 一次改五处然后看好没好 | 就算好了你也不知道是哪处起作用 |

## 例外

确实存在"重试是正解"的情况 —— 网络抖动、上游限流。但必须**先证明**是这一类:错误码是什么、失败率多少、是否随时间随机分布。证明不了就不是。

## 收尾

定位到根因后,顺手回答:

- 同类问题在代码库其它地方还有吗?
- 有没有测试能在这个 bug 再次出现时抓住它?**用刚才那条真实报错做回归用例**。
