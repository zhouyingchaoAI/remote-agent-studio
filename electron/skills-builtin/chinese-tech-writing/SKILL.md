# 中文技术写作

## 排版基本规范

- **中英文之间加空格**:`使用 Docker 部署` ✅ / `使用Docker部署` ❌
- **数字与中文之间加空格**:`耗时 3 秒`、`共 220 个测试`
- **标点用全角**,但代码、命令、路径内部保持原样:`执行 `npm test`,结果通过。`
- **不要中英标点混用**:句号用「。」不用「.」
- 括号:中文内容用「(」,纯英文内容用「(」

## 术语一致

同一份文档里一个概念只用一个说法。选定后全篇统一:

| 建议 | 避免混用 |
|---|---|
| 提交 | commit / 递交 / 提交 混用 |
| 部署 | 发布 / 上线 / 部署 混用 |
| 请求 | request / 调用 / 请求 混用 |

专有名词保留英文原文:Kubernetes、PostgreSQL、OAuth。不要译成"库伯内特斯"。

## 周报/日报:写结论,不写流水账

**读者关心的是结果和风险,不是你的操作步骤。**

❌ 流水账:
> 本周我看了代理的代码,然后调试了很久,又改了几个文件,最后测试通过了。

✅ 有信息量:
> **修复长任务中断**:代理节点间歇性返回 503,原先被判为不可重试,导致任务直接失败。现已纳入自动续跑,并补了回归用例。5 次采样验证成功率从 60% 恢复到 100%。
>
> **风险**:代理节点本身仍不稳定,建议为 API 域名固定节点。

结构模板:

```markdown
## 本周完成
- **<成果>**:<问题是什么> → <怎么解决> → <验证数据>

## 进行中
- **<事项>**:进度 <x/y>,预计 <时间>

## 风险与阻塞
- <具体问题> —— 需要 <谁> <做什么>

## 下周计划
- <可验收的目标,不是"继续优化 xx">
```

## 有数据就给数据

- ❌ "性能提升明显" → ✅ "首屏从 2.3s 降到 0.8s"
- ❌ "修了一些 bug" → ✅ "修复 3 个:附件超限、图谱空白、终端崩溃"
- ❌ "测试都过了" → ✅ "220 个测试通过,lint 无告警,构建 756ms"

## 提交信息

第一行是**一句话说清做了什么**(50 字内,不加句号),空一行后说**为什么**:

```
修复附件上传超过 20MB 被拒

工程文档(扫描件、图纸)常超过 20MB,而 SFTP 本身没有这个量级限制,
上限放宽到 200MB,主进程与前端提示同步调整。
```

不要写「修改了一些代码」「update」「fix bug」这种没有信息量的标题。

## 故障复盘

按这个顺序写,**不要跳过时间线**:

1. **影响**:什么时间、影响了谁、多久
2. **时间线**:发现 → 定位 → 处理 → 恢复,带时间点
3. **根因**:因为 A 导致 B 所以 C
4. **改进项**:每条要有负责人和时间,不写"加强监控"这种没法验收的

复盘对事不对人,写系统缺陷不写"某某疏忽"。

## 代码注释

注释写**为什么这么做**,不写**代码在做什么**:

```js
// ❌ 遍历数组
// ✅ 非交互式 SSH 不加载 ~/.bashrc,所以必须显式注入 PATH
```
